# 02. 아키텍처 및 인터페이스 계약

작성일: 2026-10-26 | 상태: **확정(v1.0)** | 스키마는 `src/schemas.py`가 단일 기준

## 1. 모듈 구성

```
GitHub 이슈 생성 이벤트
        │
        ▼
┌─────────────────────┐
│ GitHub Actions       │  .github/workflows/issue-pilot.yml
│ (트리거·실행 환경)    │  on: issues [opened]
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ ① collector          │  GitHub API → IssueInput, RepoContext
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ ② retriever          │  bge-m3 임베딩 → ChromaDB 검색 → SimilarIssue[]
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ ③ classifier (LLM)   │  IssueInput + RepoContext + SimilarIssue[]
│                      │  → Classification (Pydantic 검증, 실패 시 재요청)
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ ④ assigner           │  affected_paths + git log → AssigneeRecommendation
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ ⑤ publisher          │  PilotResult → 라벨 부착 + 코멘트 1개 + SQLite 로그
└─────────────────────┘
```

## 2. 모듈별 책임과 계약

| 모듈 | 입력 | 출력 | LLM 사용 | 외부 의존 |
|---|---|---|---|---|
| collector | 이슈 번호 | `IssueInput`, `RepoContext` | ✗ | GitHub API |
| retriever | `IssueInput`, 임베딩 저장소 | `list[SimilarIssue]` (최대 3) | ✗ | bge-m3, ChromaDB |
| classifier | `IssueInput`, `RepoContext`, `list[SimilarIssue]` | `Classification` | ✓ | Anthropic API |
| assigner | `Classification.affected_paths`, git 이력 | `AssigneeRecommendation` | ✗ | git log, GitHub API(열린 이슈 수) |
| publisher | `PilotResult` | 라벨·코멘트, 로그 행 | ✗ | GitHub API, SQLite |

**계약 규칙**
- 모듈은 자기 입력 타입만 알고, 다른 모듈의 내부를 호출하지 않는다.
- 모든 모듈은 로컬에서 단독 실행 가능해야 한다 (`python -m src.classifier --issue 12`).
- 스키마 변경은 **필드 추가만** 허용. 삭제·타입 변경은 버전 올리고 변경 이력에 기록.

## 3. LLM 호출 계약 (classifier)

- 모델: `claude-opus-5-5` (기본). 비용 비교 실험 시 `claude-haiku-5-5`로 교체 가능, 실험 로그에 기록
- 호출: Anthropic Python SDK, `output_config.format`으로 JSON 스키마 강제
- 입력 구성 순서(캐시 효율): 시스템 프롬프트(역할·규칙·Few-shot, 고정) → 저장소 컨텍스트(라벨 목록·폴더 구조, 저장소별 고정) → 유사 이슈 → 새 이슈
- 출력: `Classification` 스키마. 검증 실패 시 오류 메시지를 붙여 최대 2회 재요청
- 재현성: 같은 입력에 대해 3회 호출 유형 일치율 ≥ 90% (N3)

## 4. 데이터 흐름 예시

```
IssueInput(number=57, title="로그인 후 새로고침하면 세션이 풀립니다", body="...")
 → retriever → [SimilarIssue(number=42, similarity=0.91), ...]
 → classifier → Classification(type="bug", labels=["backend","auth"], priority="P1",
                  affected_paths=["src/auth/session.py"],
                  duplicates=[DuplicateJudgement(number=42, is_duplicate=True, reason="같은 증상")],
                  missing_info=["browser","repro_steps"])
 → assigner → AssigneeRecommendation(candidates=[("kim-dev", commits=14, open_issues=2)])
 → publisher → 라벨 [bug, backend, auth, P1] 부착 + 코멘트 1개
```

## 5. 저장소 구조 (구현 시)

```
.github/workflows/issue-pilot.yml

  schemas.py        ← 계약 (이 문서와 함께 고정)

  retriever.py
  classifier.py
  assigner.py
  publisher.py
  prompts/
    system.md       ← 프롬프트는 코드가 아니라 파일로 관리 (버전 추적)
    fewshot.json
  main.py           ← 파이프라인 조립
eval/
  eval_set.csv
  run_eval.py
data/
  embeddings/       ← ChromaDB (Actions 캐시 또는 커밋)
  pilot.sqlite      ← 분류 로그
```
